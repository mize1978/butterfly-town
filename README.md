# Butterfly Town

**小さな一手が、街の未来を変える。**

AIには意思を。Railsには責任を。

開発状況：企画・README作成段階。技術試作・実装・公開は未着手です。

## 1. サービス概要

人格・記憶・目標を持つAI住民が自律的に行動する、ミッション攻略型の街シミュレーションゲームです。

プレイヤーは街の住民として交流しながら、限られた特殊介入によって出来事や人間関係に影響を与え、街の共同目標の達成を目指します。

キャラクターや物語を楽しみたい人に、自分の選択とAI住民の意思が交わり、異なる展開が生まれる体験を提供します。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

この企画のきっかけは、AI Officeを制作していたときの体験です。

AI同士が自律的に仕事を進める様子を見て、「もし、このAIたちが喧嘩したらどうなるんだろう？」と考えました。

喧嘩したあとに仲直りするのか、対立が深まるのか、それとも第三者が巻き込まれるのか。

AI同士が自分で判断し、互いに影響を与えながら関係を変化させる世界を作ってみたいと思ったことが、この企画の出発点です。

### 2-2. なぜそれが気になったのか

私が特に興味を持っているのは、AI同士の関係性から予測できない出来事が生まれることです。

それぞれのAIが過去の出来事を記憶し、自分で判断することで、次の展開が変化する仕組みに魅力を感じています。

さらに、プレイヤー自身が働きかけた結果、住民がどう受け止め、世界がどう変化するのかを体験できるゲームにしたいと考えています。

既存のシナリオを再生するだけではなく、AIの判断とプレイヤーの選択が重なって生まれる物語を、高度なAI技術で実現することに挑戦したいです。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

キャラクターや物語を楽しむ人には、登場人物を見守るだけでなく、自分の選択によって変化する展開へ参加したいという欲求があるのではないかと考えています。

これは既存作品への不満を確認したものではなく、本作で検証したいユーザー課題の仮説です。

### 3-2. 本当に解決したい課題は何か

以下は、課題を整理するための仮説です。想定ユーザーへの確認やプレイテストを通じて検証します。

**なぜ①：なぜ物語に自分も働きかけたいのか？**

自分の選択が、登場人物や出来事に影響したと感じたいからです。

**なぜ②：なぜ自分の選択が影響したと感じたいのか？**

展開を受け取るだけでなく、その世界に参加している手応えを得たいからです。

**なぜ③：なぜその世界に参加している手応えが欲しいのか？**

自分と登場人物の選択が重なって生まれた出来事を、自分にとって特別な物語として楽しみたいからです。

**本当に解決したい課題の仮説：**

自分の働きかけに対して登場人物が意思を持って反応し、その結果として生まれる物語に参加したい。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

最初の想定ユーザーは、24歳の娘です。

PCでゲームを遊び、タワーディフェンス系、麻雀、生活シミュレーション系のゲームを楽しんでいます。

キャラクターやストーリーが好きで、気に入ったゲームを長く遊ぶタイプです。

**年齢と理由：** 身近にいる24歳の娘を最初のプレイテスト対象としているためです。他の年代との適性比較は行っていません。

**生活・利用場面：** 好きなタイミングでPCゲームを楽しみます。決まったプレイ時間帯はありません。

**利用環境：** PC。普段の利用環境に合わせ、MVPではPCブラウザを優先します。

### 4-2. 自分とユーザーの距離

**身近な誰か：娘**

ゲームの好みや遊んだ感想を直接聞けるため、初期のフィードバックを得る相手として想定しています。

### 4-3. 実際に使われる可能性について

企画について娘に話したところ、「面白そう」という反応がありました。

娘は、ハートピアのような生活シミュレーション系のゲームも楽しんでいます。

ただし、この反応だけで需要が確認できたとは考えていません。実際に遊んでもらえるか、続けて楽しんでもらえるかは未確認です。

既存のゲームを楽しむ時間の一部を本作に使いたくなるか、特に次の点を検証します。

- 住民に興味や愛着を持てるか。
- 自分の働きかけによる変化を感じられるか。
- 続きを見たい、別の方法で再挑戦したいと感じるか。

### 4-4. 利用開始・継続の流れ

1. PCブラウザでゲームを開始する。
2. すでに住民が生活している小さな街に入る。
3. 短い出来事から、祭りの準備状況や住民間の対立を知る。
4. 気になる住民を観察し、会話する。
5. 必要に応じて、特殊介入で新しい状況や機会を作る。
6. 時間を進め、住民の判断と街の変化を見る。
7. ミッション終了後、出来事と人間関係の変化を振り返る。

継続する理由として、住民のその後への関心や、異なる選択・結末を試したい気持ちが生まれることを想定しています。

登録・認証方式と、最初にサービスを知ってもらう具体的な導線は未決定です。

## 7. このアプリで実現すること

### 7-1. 基本的なゲームシステム

**AI住民の自律判断**

AI住民は、人格・記憶・目標・日課に基づいて行動を選択します。

Railsは、AIが選んだ行動の成立条件を検証し、世界の状態、進捗、勝敗を管理します。

AIの発言と実際に成立した行動は区別し、成立した出来事だけを進捗へ反映します。

**通常会話**

通常会話では、交流や情報収集に加え、説得や情報の伝達によって相手へ働きかけられます。

ただし、相手が応じる保証はありません。

特殊介入回数は消費せず、ゲーム内の時間を消費します。具体的な時間消費と影響範囲は試作で検証します。

**特殊介入**

プレイヤーは、出来事・情報・環境に働きかけ、新しい状況や機会を作れます。

特殊介入には使用回数の制限があります。

介入後もAI住民の行動を直接決定することはできず、住民は自分の人格・記憶・目標に基づいて判断します。

**時間進行**

ゲーム内の時間は朝・昼・夜を基本候補とし、時間帯ごとに住民が自律的に行動します。

介入せずに時間を進めることもできます。

具体的な時間消費量や行動回数は試作で検証します。

### 7-2. MVPで作る機能

**ゲームの核となる機能**

- PCブラウザ向けの小さな街。
- 住民ごとの人格・記憶・目標・日課。
- AIによる自律的な行動選択。
- Railsによる行動成立・状態・勝敗の管理。
- プレイヤーと住民の通常会話。
- 回数制限のある特殊介入。
- 住民同士の交流と第三者への情報伝播。
- 人間関係の変化。
- 時間帯による進行。
- 街祭りを成功させるミッション1本。
- 準備・役割の実行・重大トラブルへの対応を候補とした勝敗判定。
- 出来事と人間関係の変化を振り返る表示。

**初回体験を支える画面**

- 斜め上視点のイラスト調2Dマップ。
- 街と住民の位置表示。
- キャラクターの立ち絵と会話表示。
- 住民の歩行アニメーションを含む街の表現。

歩行や表情などの演出については、MVPへの導入方針を維持しつつ、具体的な表現範囲を試作で調整します。

**運用・安定性に関する機能**

- ゲームの保存・再開。
- AI APIの利用量制御。
- 処理失敗時の復帰。
- 同一行動の重複反映防止。

### 7-3. 技術試作で検証すること

まず3人のAI住民による技術試作を行います。

検証するのは、同じ状況でも住民が持つ記憶によって行動選択が変わるか、会話によって情報が第三者へ伝わるか、Railsが成立した行動だけを世界へ反映できるかという点です。

また、小さなマップでReactとゲーム描画ライブラリの連携を検証します。

住民数は3人の試作から開始し、10人を目標候補として費用・応答時間・見やすさを確認します。MVPの正式人数は検証後に決定します。

### 7-4. 記憶の継続と再挑戦

本作では、街の歴史を引き継ぐモードと、初期状態から再挑戦するモードの両方を実現する方針です。

**初期状態からの再挑戦：** 過去のプレイによる状態変化を引き継がず、同じミッションを別の方法で攻略できるようにします。

**歴史継続モード：** ミッションの成功・失敗にかかわらず重要な記憶を保持し、次のミッションでの判断や関係性へ反映することを目指します。

歴史継続モードの提供時期は、技術試作と複数ミッションの実装計画を踏まえて決定します。

### 7-5. MVPで検証する価値

AI住民の自律的な行動と、自分の働きかけによって生まれる変化を見て、続きを見たい、もう一度遊びたいと感じるかを検証します。

初回プレイ後に、判断の手がかり、結果への理解、続きを見たい理由や再挑戦したい理由を聞き、操作の様子と合わせて改善点を整理します。

### 7-6. 本リリースで作る機能候補

- 複数ミッションの追加。
- 初回案内と振り返り表示の改善。
- 成功・失敗時の結末や演出の充実。
- 人間関係を可視化する関係図。
- 歴史継続モードのユーザー向け提供。

具体的な実装範囲は、MVPの検証結果と開発期間を踏まえて決定します。

## 8. このアプリの懸念点とその対策

### 懸念点①：AI住民の判断が不自然になる

- **問題：** 人格や記憶と矛盾する行動をAIが選択する可能性があります。
- **理由：** 行動に一貫性がないと、プレイヤーが住民の意思を読み取れず、攻略の納得感が失われるためです。
- **対策：** 人格・目標・記憶と行動結果を記録し、条件を変えた複数回の試行で比較します。行動の成立条件はRails側で検証します。

### 懸念点②：住民が知らない情報を利用してしまう

- **問題：** 本来知らない秘密をAI住民が発言や判断に使用する可能性があります。
- **理由：** 情報伝播や誤解が重要なゲーム要素であり、情報の整合性が崩れると物語が成立しなくなるためです。
- **対策：** 世界の出来事と住民ごとの知識・記憶を分離します。情報の取得経緯と時点を記録し、本人が知る情報だけをAIに渡す設計を検証します。

### 懸念点③：通常会話と特殊介入の役割が重なる

- **問題：** 通常会話だけで特殊介入と同じ効果を得られると、特殊介入を使う意味が薄れる可能性があります。
- **理由：** 会話でも説得や情報伝達ができるため、ゲームの戦略性に影響するからです。
- **対策：** 通常会話にはゲーム内時間の消費、特殊介入には使用回数の制限を設けます。試作で攻略バランスを検証します。

### 懸念点④：AI APIの費用と応答時間が増える

- **問題：** AI住民の人数や行動回数が増えると、費用と待ち時間が増加する可能性があります。
- **理由：** 自律判断と会話にAIを利用するため、呼び出し頻度が運用費用とゲームのテンポに影響するからです。
- **対策：** 3人の技術試作でAPI使用量・応答時間・費用を計測します。呼び出し上限、タイムアウト、必要な場面だけAIを利用する構成を検討します。

### 懸念点⑤：処理失敗や二重実行でゲーム状態が壊れる

- **問題：** 同じ行動が複数回反映されたり、処理失敗によって進捗や介入回数が不正確になったりする可能性があります。
- **理由：** AIの処理結果がゲームの状態や勝敗に直接影響するためです。
- **対策：** 処理ID、DBトランザクション、重複反映防止を検討します。再試行回数に上限を設け、失敗した未確定行動は進捗に反映せず、安全に再開できる構成を検証します。

### 懸念点⑥：開発規模が大きくなる

- **問題：** AIの自律判断、記憶管理、React、ゲーム描画を組み合わせるため、開発工数が大きくなる可能性があります。
- **理由：** 複数技術の連携が必要で、現時点では実装時間と技術的難易度を検証できていないためです。
- **対策：** 3人のAI住民による試作と、小さなマップによるReact・描画ライブラリの連携検証を先行します。検証結果をもとにIssueを分割し、MVPの実装範囲を調整します。

## 9. 今後の展開・発展の方向性

MVPでは、街祭りを成功させる1つのミッションを通じて、AI住民の自律判断とプレイヤーの介入によって異なる展開が生まれるかを検証します。

### 機能追加の方向性

- 複数ミッションを追加する。
- AI住民の人数や街のエリアを拡張する。
- ミッションの成功・失敗にかかわらず、重要な記憶を次のミッションへ引き継ぐ歴史継続モードを実装する。提供時期は、技術試作と複数ミッションの実装計画を踏まえて決定する。
- 初期状態からの再挑戦と、街の歴史を引き継ぐプレイを選べるようにする。

### UI・体験の改善

- 街の歩行アニメーションやキャラクターの表情を充実させる。
- 人間関係の変化を分かりやすく示す関係図を追加する。
- 出来事の連鎖やプレイヤーの介入による影響を振り返りやすくする。

### 継続して遊ぶ価値

同じ住民でも、記憶や人間関係、プレイヤーの働きかけによって異なる展開が生まれることを目指します。

歴史継続モードでは、過去の出来事が次のミッションに影響することで、住民や街への愛着が深まる体験を目指します。

これらは今後の実装・検証対象であり、継続利用につながるかは未確認です。

## 10. 技術スタック

### 10-1. 使用予定の技術

| 項目 | 使用予定・候補 |
| --- | --- |

| デプロイ先 | AWSとPaaSを比較検討 |

### 10-2. 技術選定の比較検討

| 技術 | 判断 | 理由 |
| --- | --- | --- |
| Ruby on Rails | 採用 | ゲーム状態、行動の成立、進捗、勝敗、履歴を一元管理するため |
| React | MVPから採用 | 街の選択状態、会話、介入、進捗などのUIを連動させるため |
| Hotwire | 現方針では見送り | Rails中心に実装できる利点はあるが、今回はゲーム描画と周辺UIの連携をReactで構築することに挑戦するため |
| Phaser | 採用候補 | 2Dマップ、住民の移動、歩行アニメーションを表現するため |
| PostgreSQL | 採用候補 | 住民の関係性、個別記憶、イベント履歴を管理するため |
| 外部LLM API | 採用方針 | 人格・記憶・目標に基づく行動選択と発話に利用するため |
| ローカルLLM | 初期採用は保留 | 実行環境、日本語での判断品質、応答時間の検証が必要なため |
| AWS／PaaS | 比較中 | 費用、運用負荷、非同期処理の実行環境を比較するため |

#### 想定する役割分担

**Rails：** 世界の状態の正本を管理し、行動の成立、時間進行、ミッションの勝敗を判定します。

**React：** 会話、住民の選択、特殊介入、進捗表示などのUIを担当します。

**Phaser（候補）：** 街の描画、住民の移動、歩行アニメーションを担当します。

**外部LLM API：** 住民ごとの人格・記憶・目標と、その時点で知っている情報に基づく行動選択と発話に利用します。

これらの役割分担は設計案であり、連携の実現性は技術試作で検証します。

### 10-3. キャッチアップ不足の懸念

Railsに加えてReact、ゲーム描画ライブラリ、外部LLM APIを組み合わせるため、学習と技術検証に時間が必要になる可能性があります。

まず3人のAI住民による試作で、自律判断、個別記憶、第三者への情報伝播、Railsによる行動成立の検証を行います。

並行して、小さなマップでReactとゲーム描画ライブラリの連携を検証します。

その結果をもとにIssueを分割し、開発工数とMVPの実装範囲を見積もります。

採用するライブラリの正式なバージョン、保守状況、サポート期間は未確認のため、採用確定前に公式情報を確認します。
