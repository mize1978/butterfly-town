# Butterfly Town

**小さな一手が、街の未来を変える。**

AIには意思を。Railsには責任を。

開発状況：企画・README作成段階。固定応答による3人の技術試作を別ブランチで進めています。実LLMでの検証、本実装、公開は未着手です。

## 1. サービス概要

人格・記憶・目標を持つAI住民が自律的に行動する、ミッション攻略型の街シミュレーションゲームです。

プレイヤーは街の住民として交流しながら、限られた特殊介入によって出来事や人間関係に影響を与え、街の共同目標の達成を目指します。

キャラクターや物語を楽しみたい人に、自分の選択とAI住民の意思が交わり、異なる展開が生まれる体験を提供します。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

この企画のきっかけは、AI Officeを制作していたときの体験です。

AI同士が自律的に仕事を進める様子を見て、「もし、このAIたちが喧嘩したらどうなるんだろう？」と考えました。

喧嘩したあとに仲直りするのか、対立が深まるのか、それとも第三者が巻き込まれるのか。

AI同士が自分で判断し、互いに影響を与えながら関係を変化させる世界を作ってみたいと思ったことが、この企画の出発点です。

### 2-2. なぜそれが気になったのか

私が特に興味を持っているのは、AI同士の関係性から予測できない出来事が生まれることです。

それぞれのAIが過去の出来事を記憶し、自分で判断することで、次の展開が変化する仕組みに魅力を感じています。

さらに、プレイヤー自身が働きかけた結果、住民がどう受け止め、世界がどう変化するのかを体験できるゲームにしたいと考えています。

既存のシナリオを再生するだけではなく、AIの判断とプレイヤーの選択が重なって生まれる物語を、高度なAI技術で実現することに挑戦したいです。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

キャラクターや物語を楽しむ人には、登場人物を見守るだけでなく、自分の選択によって変化する展開へ参加したいという欲求があるのではないかと考えています。

これは既存作品への不満を確認したものではなく、本作で検証したいユーザー課題の仮説です。

### 3-2. 本当に解決したい課題は何か

以下は、課題を整理するための仮説です。想定ユーザーへの確認やプレイテストを通じて検証します。

**なぜ①：なぜ物語に自分も働きかけたいのか？**

自分の選択が、登場人物や出来事に影響したと感じたいからです。

**なぜ②：なぜ自分の選択が影響したと感じたいのか？**

展開を受け取るだけでなく、その世界に参加している手応えを得たいからです。

**なぜ③：なぜその世界に参加している手応えが欲しいのか？**

自分と登場人物の選択が重なって生まれた出来事を、自分にとって特別な物語として楽しみたいからです。

**本当に解決したい課題の仮説：**

自分の働きかけに対して登場人物が意思を持って反応し、その結果として生まれる物語に参加したい。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

最初の想定ユーザーは、24歳の娘です。

PCでゲームを遊び、タワーディフェンス系、麻雀、生活シミュレーション系のゲームを楽しんでいます。

キャラクターやストーリーが好きで、気に入ったゲームを長く遊ぶタイプです。

**年齢と理由：** 身近にいる24歳の娘を最初のプレイテスト対象としているためです。他の年代との適性比較は行っていません。

**生活・利用場面：** 好きなタイミングでPCゲームを楽しみます。決まったプレイ時間帯はありません。

**利用環境：** PC。普段の利用環境に合わせ、MVPではPCブラウザを優先します。

### 4-2. 自分とユーザーの距離

**身近な誰か：娘**

ゲームの好みや遊んだ感想を直接聞けるため、初期のフィードバックを得る相手として想定しています。

### 4-3. 実際に使われる可能性について

企画について娘に話したところ、「面白そう」という反応がありました。

娘は、ハートピアのような生活シミュレーション系のゲームも楽しんでいます。

ただし、この反応だけで需要が確認できたとは考えていません。実際に遊んでもらえるか、続けて楽しんでもらえるかは未確認です。

既存のゲームを楽しむ時間の一部を本作に使いたくなるか、特に次の点を検証します。

- 住民に興味や愛着を持てるか。
- 自分の働きかけによる変化を感じられるか。
- 続きを見たい、別の方法で再挑戦したいと感じるか。

### 4-4. 利用開始・継続の流れ

1. PCブラウザでゲームを開始する。
2. すでに住民が生活している小さな街に入る。
3. 短い出来事から、祭りの準備状況や住民間の対立を知る。
4. 気になる住民を観察し、会話する。
5. 必要に応じて、特殊介入で新しい状況や機会を作る。
6. 時間を進め、住民の判断と街の変化を見る。
7. ミッション終了後、出来事と人間関係の変化を振り返る。

継続する理由として、住民のその後への関心や、異なる選択・結末を試したい気持ちが生まれることを想定しています。

登録・認証方式と、最初にサービスを知ってもらう具体的な導線は未決定です。

## 7. このアプリで実現すること

### 7-1. 基本的なゲームシステム

**AI住民の自律判断**

AI住民は、人格・記憶・目標に基づいて、重要な行動を自分で選びます。

Railsは、日課の実行と、判断のきっかけになる状況の検出を担当します。検出する状況は、新しい情報を得た、誘われた、対立が起きた、目標同士が衝突した、などです。

AIは、こうした状況で人格・記憶・目標を踏まえて、誘う・相談する・情報を伝える・断るなどの重要な行動を選びます。

AIが立てた計画はすぐに捨てず、次の時間帯以降も継続します。状況が変わったときに再判断する設計方針です。

Railsは、AIが選んだ行動の成立条件を検証し、世界の状態、進捗、勝敗を管理します。

AIの発言と実際に成立した行動は区別し、成立した出来事だけを進捗へ反映します。

AI APIの予算が不足した場合でも、Railsが住民の代わりに重要な判断を行う設計にはしません（「8. 懸念点④」を参照）。

**通常会話**

通常会話では、交流や情報収集に加え、説得や情報の伝達によって相手へ働きかけられます。

ただし、相手が応じる保証はありません。

特殊介入回数は消費せず、ゲーム内の時間を消費します。具体的な時間消費と影響範囲は試作で検証します。

**特殊介入**

プレイヤーは、出来事・情報・環境に働きかけ、新しい状況や機会を作れます。

特殊介入は1プレイ3回までです。

介入後もAI住民の行動を直接決定することはできず、住民は自分の人格・記憶・目標に基づいて判断します。

**時間進行**

1プレイは5日間で、各日を朝・昼・夜に分けた合計15時間帯で進行します。

時間帯ごとに、Railsが日課を実行し、判断が必要な住民はAIが行動を選びます。

介入せずに時間を進めることもできます。

1時間帯あたりの行動回数や、通常会話による時間消費量は試作で検証します。

### 7-2. MVPの完成範囲

卒業制作では、次の範囲をMVPとして完成させます。

| 項目 | MVPで完成させる内容 |
| --- | --- |
| 住民 | AI住民3人 |
| 舞台とミッション | 小さな街と、街祭りを成功させるミッション1本 |
| 時間 | 5日間・朝昼夜の15時間帯 |
| プレイヤーの働きかけ | 通常会話と、1プレイ3回の特殊介入 |
| AIの判断 | 人格・記憶・目標に基づく自律判断 |
| 情報 | 住民間の情報伝播 |
| ゲーム管理 | Railsによる行動成立・進捗・勝敗判定 |
| 画面 | 小さな街の表示、住民の簡単な移動、会話・進捗表示 |
| 終了後 | 結果・関係性の振り返りと、初期状態からの再挑戦 |

**MVPの対象外**

- 住民の10人化。
- 複数ミッション。
- 歴史継続モード（重要な記憶を次のミッションへ引き継ぐモード）。
- 歩行アニメーションや表情などの複雑な演出。
- ゲーム中に動的に発生する重大トラブル。

これらは「7-6. 本リリースで作る機能候補」と「9. 今後の展開」で扱います。

**運用・安定性に関する機能（MVPに含める）**

- ゲームの保存・再開。
- AI APIの予算管理（「8. 懸念点④」と「10-4」を参照）。
- 処理失敗時の復帰。
- 同一行動の重複反映防止。

### 7-3. 技術試作で検証すること

MVPと同じ3人のAI住民で技術試作を行います。

検証するのは、同じ状況でも住民が持つ記憶によって行動選択が変わるか、会話によって情報が第三者へ伝わるか、Railsが成立した行動だけを世界へ反映できるかという点です。

現在は、実LLMの代わりに固定応答を使った試作を別ブランチで進めています。実LLMによる判断の品質、費用、応答時間は未検証です。

また、小さなマップでReactとゲーム描画ライブラリの連携を検証します。

### 7-4. 再挑戦

MVPでは、初期状態からの再挑戦を提供します。過去のプレイによる状態変化を引き継がず、同じミッションを別の方法で攻略できるようにします。

ミッションの成功・失敗にかかわらず重要な記憶を次のミッションへ引き継ぐ歴史継続モードは、MVPの対象外です。複数ミッションが前提になるため、本リリース以降の候補とします。

### 7-5. MVPで検証する価値

AI住民の自律的な行動と、自分の働きかけによって生まれる変化を見て、続きを見たい、もう一度遊びたいと感じるかを検証します。

初回プレイ後に、判断の手がかり、結果への理解、続きを見たい理由や再挑戦したい理由を聞き、操作の様子と合わせて改善点を整理します。

### 7-6. 本リリースで作る機能候補

- 複数ミッションの追加。
- 歴史継続モード。
- AI住民の10人への拡張。
- 歩行アニメーションや表情などの演出の充実。
- ゲーム中に動的に発生する重大トラブル。
- 人間関係を可視化する関係図。
- 初回案内と振り返り表示の改善。

具体的な実装範囲は、MVPの検証結果、開発期間、AI APIの費用を踏まえて決定します。

## 8. このアプリの懸念点とその対策

### 懸念点①：AI住民の判断が不自然になる

- **問題：** 人格や記憶と矛盾する行動をAIが選択したり、時間帯ごとに方針がぶれたりする可能性があります。
- **理由：** 行動に一貫性がないと、プレイヤーが住民の意思を読み取れず、攻略の納得感が失われるためです。
- **対策：** AIが立てた計画を保存して次の時間帯以降も継続し、状況が変わったときだけ再判断する設計にします。人格・目標・記憶と行動結果を記録し、条件を変えた複数回の試行で比較します。行動の成立条件はRails側で検証します。

### 懸念点②：住民が知らない情報を利用してしまう

- **問題：** 本来知らない秘密をAI住民が発言や判断に使用する可能性があります。
- **理由：** 情報伝播や誤解が重要なゲーム要素であり、情報の整合性が崩れると物語が成立しなくなるためです。
- **対策：** 世界の出来事と住民ごとの知識・記憶を分離します。情報の取得経緯と時点を記録し、本人が知る情報だけをAIに渡す設計を検証します。

### 懸念点③：通常会話と特殊介入の役割が重なる

- **問題：** 通常会話だけで特殊介入と同じ効果を得られると、特殊介入を使う意味が薄れる可能性があります。
- **理由：** 会話でも説得や情報伝達ができるため、ゲームの戦略性に影響するからです。
- **対策：** 通常会話にはゲーム内時間の消費、特殊介入には1プレイ3回の上限を設けます。試作で攻略バランスを検証します。

### 懸念点④：AI APIの費用が予算を超える・予算不足で判断が止まる

- **問題：** 呼び出し回数や入出力の長さが増えると、月の予算を超える可能性があります。また、予算が尽きたときにAIの判断を続けられなくなります。
- **理由：** AI API予算は月3,000円以内であり、自律判断と会話にAIを利用するため、呼び出し頻度が費用とゲームのテンポに直接影響するからです。
- **対策：**
  - 住民の行動判断でAIを呼ぶのは、Railsが新情報・誘い・対立・目標の衝突などを検出したときに限ります。日課はRailsが実行します。
  - ゲーム内の判断だけでなく、会話・要約・再試行・開発検証で使う分も、同じ月予算で管理します。
  - 月2,000円相当に達したら新しいAI呼び出しを止める案を、安全余裕の候補とします。残りの約1,000円は、為替・税・請求額の差異に備える予備枠として扱います。
  - 予算が不足した場合、Railsが重要なAI判断を代行することはしません。その時間帯を確定させずにゲームを保存し、安全に中断します。
  - 試算と、未解決の設計課題（呼び出し前の費用予約、同時実行時の予算管理、結果が不明な呼び出しの扱い）は「10-4」に記載します。
  - 応答時間は、3人の技術試作で実測してから、タイムアウトと待ち時間の表示方法を決めます。

### 懸念点⑤：処理失敗や二重実行でゲーム状態が壊れる

- **問題：** 同じ行動が複数回反映されたり、処理失敗によって進捗や介入回数が不正確になったりする可能性があります。
- **理由：** AIの処理結果がゲームの状態や勝敗に直接影響するためです。
- **対策：** 処理ID、DBトランザクション、重複反映防止を検討します。再試行回数に上限を設け、失敗した未確定行動は進捗に反映せず、安全に再開できる構成を検証します。古い状態をもとに作られた行動案を後から反映しない仕組みも検討します。

### 懸念点⑥：開発規模が大きくなる

- **問題：** AIの自律判断、記憶管理、React、ゲーム描画を組み合わせるため、開発工数が大きくなる可能性があります。
- **理由：** 複数技術の連携が必要で、現時点では実装時間と技術的難易度を検証できていないためです。
- **対策：** MVPの範囲を「7-2」に固定し、10人化・複数ミッション・歴史継続モード・複雑な演出・動的な重大トラブルは対象外にします。3人のAI住民による試作と、小さなマップによるReact・描画ライブラリの連携検証を先行し、検証結果をもとにIssueを分割します。

## 9. 今後の展開・発展の方向性

MVPでは、AI住民3人と街祭りミッション1本を通じて、AI住民の自律判断とプレイヤーの介入によって異なる展開が生まれるかを検証します。

以下はMVPの対象外で、MVPの検証結果、開発期間、AI APIの費用を踏まえて取り組む候補です。

### 機能追加の方向性

- 複数ミッションを追加する。
- AI住民を10人に拡張し、街のエリアを広げる。
- ミッションの成功・失敗にかかわらず、重要な記憶を次のミッションへ引き継ぐ歴史継続モードを実装する。
- 初期状態からの再挑戦と、街の歴史を引き継ぐプレイを選べるようにする。
- ゲーム中に動的に発生する重大トラブルを追加する。

### UI・体験の改善

- 住民の歩行アニメーションやキャラクターの表情などの演出を充実させる。
- 人間関係の変化を分かりやすく示す関係図を追加する。
- 出来事の連鎖やプレイヤーの介入による影響を振り返りやすくする。

### 継続して遊ぶ価値

同じ住民でも、記憶や人間関係、プレイヤーの働きかけによって異なる展開が生まれることを目指します。

歴史継続モードでは、過去の出来事が次のミッションに影響することで、住民や街への愛着が深まる体験を目指します。

これらは今後の実装・検証対象であり、継続利用につながるかは未確認です。

### 10-2. 技術選定の比較検討

| 技術 | 判断 | 理由 |
| --- | --- | --- |
| Ruby on Rails | 採用 | ゲーム状態、行動の成立、進捗、勝敗、履歴を一元管理するため |
| React | MVPから採用 | 街の選択状態、会話、介入、進捗などのUIを連動させるため |
| Hotwire | 現方針では見送り | Rails中心に実装できる利点はあるが、今回はゲーム描画と周辺UIの連携をReactで構築することに挑戦するため |
| Phaser | 採用候補 | 2Dマップの表示と、住民の簡単な移動を表現するため |
| PostgreSQL | 採用候補 | 住民の関係性、個別記憶、イベント履歴を管理するため |
| 外部LLM API | 採用方針 | 人格・記憶・目標に基づく行動選択と発話に利用するため |
| ローカルLLM | 初期採用は保留 | 実行環境、日本語での判断品質、応答時間の検証が必要なため |
| AWS／PaaS | 比較中 | 費用、運用負荷、非同期処理の実行環境を比較するため |

#### 想定する役割分担

**Rails：** 世界の状態の正本を管理します。日課の実行、判断のきっかけになる状況の検出、行動の成立、時間進行、ミッションの勝敗、AI APIの予算を管理します。

**React：** 会話、住民の選択、特殊介入、進捗表示などのUIを担当します。

**Phaser（候補）：** 街の描画と、住民の簡単な移動を担当します。

**外部LLM API：** 住民ごとの人格・記憶・目標と、その時点で知っている情報に基づく重要な行動の選択、計画、発話に利用します。DBを直接更新することはありません。

これらの役割分担は設計案であり、連携の実現性は技術試作で検証します。

### 10-3. キャッチアップ不足の懸念

Railsに加えてReact、ゲーム描画ライブラリ、外部LLM APIを組み合わせるため、学習と技術検証に時間が必要になる可能性があります。

まず3人のAI住民による試作で、自律判断、個別記憶、第三者への情報伝播、Railsによる行動成立の検証を行います。

採用するライブラリの正式なバージョン、保守状況、サポート期間は未確認のため、採用確定前に公式情報を確認します。

### 10-4. AI APIの費用試算と予算管理

AI APIの予算は月3,000円以内とします。

以下は、Claude Haiku 5.5の[公式掲載単価](https://platform.claude.com/docs/en/about-claude/pricing)（2026-10-25参照）を参考にした**試算**です。実測ではありません。また、使用するモデルは正式に決まっていません。

| 条件 | 値 |
| --- | --- |
| 入力単価 | 100万トークンあたり $0.10 |
| 出力単価 | 100万トークンあたり $0.50 |
| 1プレイのAI呼び出し回数 | 30回（仮定。内訳は未確定） |
| 1回あたりの平均トークン数 | 入力2,000・出力300（仮定） |
| 為替 | 1ドル150円（仮定） |

| 計算 | 結果 |
| --- | --- |
| 1回あたり | 入力 $0.0002 ＋ 出力 $0.00015 ＝ $0.00035 |
| 1プレイ（30回） | $0.0105 ≒ **約1.58円** |
| 月300プレイ | $3.15 ≒ **約473円** |

**試算の前提と注意点**

- 上の単価は、1回のプロンプトが10万トークン以下の場合のものです。10万トークンを超える呼び出しは、より高い単価になります。
- 単価は米ドル表示です。税と為替の変動は試算に含めていません。
- 呼び出し回数とトークン数は仮定です。3人の技術試作で、実LLMを使って実測してから見直します。
- 30回の内訳（住民の行動判断・通常会話・要約をどこまで含むか）は未確定です。再試行と開発検証の分は、上の試算に含めていません。
- 会話・要約・再試行・開発検証で使う分も、すべて同じ月3,000円の予算で管理します。

**予算の使い方（案）**

- 月2,000円相当に達したら、新しいAI呼び出しを止めることを安全余裕の候補とします。
- 残りの約1,000円は、為替・税・請求額の差異に備える予備枠として扱います。

**予算不足時の方針**

- 予算が不足しても、Railsが重要なAI判断を代行することはしません。
- その時間帯を確定させずにゲームを保存し、安全に中断します。予算が回復してから再開できるようにします。

**未解決の設計課題**

- **呼び出し前の費用予約：** 実際の費用は応答が返るまで分かりません。呼び出す前に、最大出力トークン数などから上限額を見積もって予算を予約し、応答後に実際の額で精算する方式を検討します。
- **同時実行時の予算管理：** 複数の呼び出しが同時に予算を確認すると、全員が「残りがある」と判断して上限を超える可能性があります。予約をDBで原子的に行う方式を検討します。
- **結果が不明な呼び出しの扱い：** タイムアウトや通信エラーで、課金されたかどうか分からない呼び出しが起こり得ます。課金された前提で予約額を消費扱いにし、自動再試行による二重の費用を防ぐ方式を検討します。

いずれも方式は未決定で、実装と検証はこれからです。
