# 描画Spike（React＋Phaser 4 / Canvas 2D）結果

実施日：2026-10-26　ブランチ：`feature/render-spike`（`feature/three-resident-spike` の `382974d` から作成）

固定データだけで行った描画と操作の技術検証です。AI住民・Rails・修理パズルとは接続していません。人物・衣装・素材は Art Prototype 02（歩行比較版 v2）の試作で、本番素材ではありません。

## 起動方法

```sh
cd render-spike
npm ci                 # 依存はこのフォルダの node_modules にだけ入る
npm run art            # ~/outputs の試作素材を public/art へ複製（元は変更しない。SHA-256で一致を確認）
npm run dev            # http://127.0.0.1:4190/  （?renderer=canvas で Canvas 版から開始）
```

画面右上の「Phaser 4／Canvas 2D」で、同じ状態のまま描画方式を切り替えられます。`?stress=500` を付けると、比較用に歩く人物を500体追加します。

## 構成

```
src/core/       描画エンジンに依存しない部分（node でテスト）
  world.ts        通行ポリゴン・衝突・移動（AP02 の engine.mjs を移植）
  appearance.ts   人物×衣装×場面×歩行コマ → 画像と切り出し範囲
  sim.ts          長押しの移動状態
src/state/      React 側の正本（人物・衣装・乗車）と、描画との照合
src/render/     PhaserRenderer / CanvasRenderer（同じ core・入力・素材を使う）
src/ui/         React の画面。描画をマウントし、アンマウントで破棄する
e2e/            ヘッドレス Chrome の実マウス入力による検証
```

- 状態の正本は React 側のストア（Session）です。描画側は毎フレーム `session.tick()` を呼んで移動を1コマ分進めます（時計の役割）。人物・衣装・乗車状態は読むだけで、コピーを持ちません。
- 衝突は Phaser の物理エンジンを使わず、共通の多角形判定で扱います（Arcade Physics は矩形と円だけ）。
- 手前の植栽は、背景から切り抜いた透過画像を人物の上に重ねています（両方式で共通）。Phaser 4 では GeometryMask が廃止され、WebGL ではマスクを filter として扱う方式に変わったため、事前に切り抜く方式を採りました。

## Phaser と Canvas の比較

計測は `node e2e/perf.mjs`（生データは `e2e/out/perf.json`）で行いました。

計測条件
- ヘッドレス Chrome（ANGLE Metal、Apple M5）、1440×900、DPR 1、キャッシュ無効。
- 追加人物の数ごとに、各方式を3回測った**中央値**です。
- **準備時間**：「街へ」を押してから、素材の読み込みと最初の1フレームの描画が終わるまで（両方式とも同じ基準）。
- **1フレーム**：1秒のウォームアップの後に計測区間をリセットし、続く3秒間の「更新＋描画命令」の CPU 時間を測ったもの。GPU の実行時間は含みません。
- 低性能な PC やスマホでの値ではありません。

| 追加人物 | 方式 | 準備時間 | fps | 1フレーム平均 | p95 | JSヒープ |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | Phaser WebGL | 435ms | 60 | 0.35ms | 0.6ms | 81MB |
| 0 | Canvas 2D | 86ms | 60 | 0.09ms | 0.2ms | 79MB |
| 100 | Phaser WebGL | 437ms | 60 | 0.56ms | 0.8ms | 80MB |
| 100 | Canvas 2D | 126ms | 60 | 0.88ms | 1.2ms | 81MB |
| 500 | Phaser WebGL | 421ms | 60 | 1.07ms | 1.4ms | 92MB |
| 500 | Canvas 2D | 145ms | 60 | 2.61ms | 3.9ms | 91MB |
| 1000 | Phaser WebGL | 487ms | 60 | 1.70ms | 2.9ms | 90MB |
| 1000 | Canvas 2D | 138ms | 60 | 2.84ms | 4.3ms | 84MB |

**測るたびに値がぶれます。** 直前の実行では、Phaser の1000体が平均0.93ms、Canvas の500体が1.50msでした。表の数値そのものではなく、傾向として読んでください。傾向（1体では Canvas が軽い、人物が多いと Phaser の伸びが小さい、準備は Canvas が速い）は、これまでの3回の実行で変わっていません。

perf.mjs は、全8条件それぞれで有効な計測が3回そろわなければ、失敗として終了します。「有効」とは次の条件をすべて満たすものです。
- 想定どおりの描画方式。
- 標本100以上、有限値。
- 計測区間3秒のうち2.7秒以上を覆っている。
- 取得の直前（200ms以内）まで描画が続いている。

**出どころの記録**：`perf.json` と `result.json` には、試験の開始時と終了時に計算したローカルファイルの SHA-256 を記録しています。対象は src・e2e・public/art・設定・依存の固定です。今回の値は、どちらも開始時と終了時で同じ `d67cbec7…` です。開発サーバーが実際に配信した内容との照合まではしていません。

読み取れること
- どちらの方式も、この環境では1000体まで60fpsを保ちました。
- 人物が1体だけなら Canvas の方が軽く、100体でほぼ同じ、それ以上では Phaser の方が CPU 時間の伸びが小さくなります。
- 準備は Canvas の方が速いです。Phaser が遅い理由（WebGL の初期化やテクスチャ転送など）は、内訳を測っていないため特定していません。

| 観点 | Phaser 4 | Canvas 2D |
| --- | --- | --- |
| 本番画風の再現性 | 同じ画像を同じ大きさで表示。人物を拡大して比べても違いは見つからない（DPR 1 のスクリーンショット） | 同じ |
| 描画性能 | 上の表のとおり。人物が多いときに有利、準備は遅い | 1体なら最も軽い。人物の数にほぼ比例して増える |
| 歩行アニメーション | 歩行シートの各コマをテクスチャのフレームとして登録。将来アトラスやアニメ機能へ移りやすい | 切り出し範囲を毎回指定して描く |
| 衣装切り替え | 共通の外見解決を使うため同じ（全組み合わせで確認） | 同じ |
| 当たり判定 | 共通の TS（エンジン非依存）。Arcade は使わない | 同じ |
| React との連携 | READY を待ってシーンを追加。破棄は次のフレームなので DESTROY を待って完了とする。読み込み中の破棄と、読み込み失敗時の破棄に対策が必要だった（実装済み） | 生成と破棄が単純 |
| 実装・保守の負担 | 依存が増える（本体の JS が 1.6MB、gzip 433KB）。Phaser 4 は API の変更が大きく（例：GeometryMask の廃止）、資料に版の混在がある | カメラ・深度の並べ替え・素材の読み込み・アニメ・高 DPI 対応を自分で書く必要がある |

### 推奨

**Phaser 4 を第一候補として、本体の描画の土台に使うことを提案します。** ただし採用を確定するのは、下の「未検証」のうち、低性能な端末での性能と、本番規模のマップでのカメラ・深度の確認を終えてからにします。移動・衝突・外見の解決・状態は、今回のようにエンジンに依存しない `core` と React 側のストアに置きます。こうしておけば、描画層だけを Canvas 版へ戻すこともできます（同じ core で両方が動くことを今回示しました）。

理由
- 本番では人物（主役3人・店主・プレイヤー）、前景のレイヤー、カメラ追従、アトラス、アニメが増えます。人物が多いときの CPU 時間の伸びは、Phaser の方が小さく出ました。
- カメラ・素材の読み込み・深度・アニメを自作せずに済みます。
- StrictMode の二重実行、描画方式の連続切り替え、読み込み中の破棄（素材の通信を保留して確定させた状態）、読み込み失敗のいずれでも、破棄が完了することを確認しました。

注意点：準備に約0.4〜0.5秒かかることと、本体の JS が大きい（gzip 433KB）ことです。読み込み中の表示とコード分割が必要です。長時間動かしたときのメモリの推移は測っていません。

## テスト結果

| 確認項目 | 方法 | 結果 |
| --- | --- | --- |
| 型検査 | `npx tsc --noEmit` | エラー0 |
| 通行判定・移動（AP02 から移植） | vitest `world.test.ts`（全方向×徒歩・乗車、ランダム10,000回など） | 通過 |
| 長押し・離すと停止・境界停止・歩行コマ | vitest `sim.test.ts` | 通過 |
| 全組み合わせの外見解決・乗車中に歩行コマを混ぜない | vitest `appearance.test.ts` | 通過 |
| 衣装を人物ごとに保持（男女で別の衣装）・狭い場所では乗れない・4種類の画面遷移で入力を解除・照合の検出力 | vitest `session.test.ts` | 通過 |
| 実ブラウザでの操作（男女×Phaser・Canvas） | `node e2e/browser-check.mjs`（CDP の実マウス入力） | **90/90 通過**、想定外のエラー・警告0（想定どおりとして除外したログ13件は `result.json` の excluded に保存） |
| 性能比較 | `node e2e/perf.mjs` | 上の表（3回の中央値） |
| Spike 01 を壊していない | `docker compose run --rm web bin/rails test` | 26 runs, 100 assertions, 0 failures（backend の差分なし） |

vitest は4ファイル・16テストです。

**状態と描画の照合**は、次のように行っています。
- 描画側は、実際に描いた値を記録します。Phaser は表示オブジェクトのテクスチャ・フレーム名・反転・位置、Canvas は drawImage に渡した画像・切り出し範囲・変換行列です。
- 照合する側は、React の状態と移動状態から「描かれるべき画像・コマ・向き・位置」を独立に求めます。
- 状態は入力や操作でフレームの途中に変わるため、照合は新しいフレームが描かれるのを待ってから行います。1秒以内に新しい描画を確認できない場合と、待っている間に描画方式が変わった場合は、不一致として扱います。
- 画像・コマ・向き・位置のどれか1つでもずれれば検出できることを、単体テストで確認しています。

e2e で確かめたこと（男女×2方式のそれぞれで）
- 選んだ人物が表示される。
- 長押しで移動し、離すと止まって立ち姿に戻る。
- 歩行4コマを再生する。
- 水路と建物の方向へ6秒押し続けても、60回の標本すべてで通行範囲の中に留まり、境界で止まる。
- 衣装差分に切り替えても、同じ人物・同じ位置のまま。
- 狭い場所では乗車を断る。
- 乗車すると同じ衣装の乗車姿になり、乗車中の移動量が100以上、歩行コマを混ぜない。
- 降車しても衣装はそのまま。
- 移動中・乗車中に、100msごとに照合する。
- 選択画面に戻ると、破棄が完了するまで待って確認する。
- 男女で別の衣装にして選び直すと、それぞれの衣装で表示される。

全体での確認
- 描画方式を3回切り替えても、生きている描画は1つ。
- 30ms間隔で方式を6回切り替え、入退場もすると、すべて破棄が完了し、再入場後の照合も一致する。
- **読み込み中の破棄**：CDP の Fetch 機能で素材の通信を保留し、「読み込み中」（保留1件以上・status=loading。今回の実績は条件により1〜14件）を確定させてから、退場と方式の切り替えをそれぞれ行う。保留を解除した後も、破棄した描画が再初期化されず、生存数は退場なら0、切り替えなら新しい描画1つになる（Phaser・Canvas の両方）。
- 素材が無いと、エラーを表示して描画を破棄する（Phaser・Canvas の両方）。除外するのは、存在しない素材ファイルへの通信エラー（発生元が network で、URL が素材名と一致するもの）と、Phaser が素材ごとに出す既知の通知だけ。実行時例外は除外しない。CDP の操作（通信保留の解除など）の応答エラーは、試験の失敗として扱う。
- 試験の開始時と終了時で、対象ファイルのハッシュが一致する（途中で変更して元に戻した場合までは検出できない）。

## 未検証

- 人の目での操作感（みぜの試遊）。Safari・Firefox・Magic Mouse・トラックパッド。
- 高 DPI（Retina、DPR 2）での画質。今回の論理解像度は 1536×1024 固定。
- 低性能な PC・スマホでの性能、ヘッドレス以外の Chrome での計測、長時間の連続動作でのメモリ（リークが無いことまでは確認していない。確認したのは破棄の完了まで）。
- 方向転換は左右の反転だけ。正面・背面の素材がない。
- 本番マップの規模でのカメラ追従・深度の並べ替え・前景の精密な切り抜き。
- Rails からの状態取得（今回は React のストアだけ）。素材の権利条件。

## 監査で残った軽微な指摘（未対応）

- ブラウザ検証は、CDP の Log ドメインのうち error だけを集めていて、warning は集めていない。
- 素材が無いときの通信エラーを除外する条件は、発生元と URL だけで、失敗理由や HTTP ステータスまでは確かめていない。
- 性能計測（`e2e/perf.mjs`）は、CDP の応答エラーを確かめていない。

## 次の本体実装に必要な作業

1. 本体の frontend の構成を決める（この `render-spike` を土台にするか、既存の `frontend/` を作り直すか）。Node・パッケージの版を固定する。
2. Rails の API と React のストアをつなぐ（外見・乗車状態の保存、world-snapshot・state_version）。Spike 02 の確認事項の判断も必要。
3. 描画層を Phaser で本番の構成へ広げる（カメラ、深度の並べ替え、前景のレイヤー、読み込み中の表示、コード分割）。
4. 本番素材の制作範囲を決める（方向数、衣装数、権利の確認）。
5. 操作感をみぜが試遊して評価し、速度・不感帯・乗車の判定幅を調整する。
